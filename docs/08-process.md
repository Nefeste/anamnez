# Как ведётся работа

Процесс повторяет «Вотчину» — он там проверен до магазинов. Здесь записано, что
переносится как есть, что меняется и что добавляется из-за медицинской базы.

## Жизненный цикл возможности

Как во всех проектах студии: спецификация → код и тесты → проверка → документы → версия и выпуск
([устав, «Жизненный цикл возможности»](https://github.com/Nefeste/gornitsa/blob/main/docs/04-process.md#жизненный-цикл-возможности)).
Здесь: сначала движок и его тесты, потом экраны; проверки — [`09-testing.md`](09-testing.md), минимум
перед релизом — типы, линтер, тесты движка, валидатор базы, «виртуальный врач», сценарий в браузере,
для карты и звука — телефон; правятся `03`–`07` и [`10-roadmap.md`](10-roadmap.md).

## Поток медицинской базы

Параллельно возможностям идёт наполнение базы (`05-content.md`). Для него спецификация
не пишется; порядок такой:

1. Пачка записей одного отделения (5–10 состояний со своими признаками и
   обследованиями), каждая — `review: draft`, с источниками. Рекомендацию Минздрава
   записывают по рубрикатору (`05-content.md` §2): название, год, ID и ссылка на карточку.
2. `npm run content` — сборка и валидатор; `npm run doctor` — «виртуальный врач» по
   отделению. Отчёт (точность, цена, путаницы) — в описание коммита.
3. Сверка владельцем по источникам → `checked`; неотложные — консультанту → `reviewed`.
4. Поднять `contentVersion`, если пачка уходит в выпуск, и дописать новые идентификаторы в
   список выпущенных: `bun tools/content/released-ids.ts` (ADR 0011).

## Версии

Что значат три числа, как считается `versionCode` и что 1.0.0 — первый выход в магазин, записано
в уставе ([«Версии»](https://github.com/Nefeste/gornitsa/blob/main/docs/04-process.md#версии)).
Здесь — как номер привязан к этапам дорожной карты (`10-roadmap.md`, «Этапы»):

- **третье число** растёт с каждой частью — PR с тестами и документами — и с исправлениями;
  **второе** — на границе этапа: этап 2 — 0.1.0, этап 3 — 0.2.0, этап 4 — 0.3.0 и так далее;
- граница этапа — когда его части сделаны в коде; проверки с людьми (вопросы владельцу) номер
  не держат. До 29.09.2026 номер ждал живой проверки этапа 2 и застрял на 0.0.x до 0.0.55;
  с части 32в — 0.2.0 (отзыв владельца);
- у базы — свой номер `contentVersion` (`content/version.yaml`), растёт при каждом
  выпуске с изменённой базой; оба номера видны в «Об игре» и в отчёте об ошибке.

### Где лежит номер версии

Как в «Вотчине», в нескольких местах; сверяет их `tools/test/version.test.ts`.

| Файл | Что поправить |
|------|---------------|
| `app.json` | `expo.version` и `expo.android.versionCode` (+1); игра показывает версию из этого же файла (`src/info.ts`) |
| `package.json` | `version` |
| `package-lock.json` | `npm install --package-lock-only` (номер поднимается **до** установки) |
| `src/i18n/sections/about.ts` | `news` — «Что нового» в «Об игре» |
| `content/version.yaml` | `contentVersion`, если база менялась |

Каждой версии — раздел в корневом `README.md` (правило устава); «Что нового» в игре — то же, короче.

## Сборка и выкладывание

Автоматика — перенос из «Вотчины» с правками; откуда и с какого коммита — первая строка файла
(`# из votchina: <путь> @ <коммит>`, устав, «Общий код игр»). Сервера нет, поэтому `worker.yml`
не нужен.

| Workflow | Когда | Что делает |
|----------|-------|------------|
| `.github/workflows/pr.yml` | на каждый PR в `main`, и на документах тоже; черновик — когда готов к ревью | быстрые проверки (ADR студии [0019](https://github.com/Nefeste/gornitsa/blob/main/adr/0019-ci-on-pr.md)): сборка и валидатор базы, типы приложения и инструментов, линтер, тесты — задание «Проверки PR», обязательное для слияния. Без prebuild, Gradle и APK |
| `.github/workflows/automerge.yml` | метка на PR поставлена или снята, новый коммит, конец проверок PR | автослияние (ADR студии [0018](https://github.com/Nefeste/gornitsa/blob/main/adr/0018-change-classes-automerge.md)): метка `ревью: ок`, зелёные «Проверки PR» и ни одной красной или незаконченной проверки на последнем коммите, ни одного пути владельца — auto-merge GitHub (squash). Новый коммит снимает метку, снятая метка выключает автослияние. Правила и разбор путей (`.github/scripts/owned.mjs`, перенос из «Вотчины») берёт из `main`, а не из PR ([«Слияние»](#слияние)) |
| `.github/workflows/android.yml` | тег `vX.Y.Z` — его ставит владелец; ручного запуска нет (решение владельца, 03.10.2026) | задание «проверки»: типы, линтер, тесты, сборка и валидатор базы, короткий прогон «виртуального врача»; веб-сборка со сценарием Playwright, сборка APK; релиз `vX.Y.Z` с ним. Слияние в `main` сборку не запускает (ADR студии 0019): сценарий и «виртуального врача» агент гоняет у себя перед каждым push, а в сборке они — ворота релиза |
| `.github/workflows/doctor.yml` | изменения `content/**`, `src/engine/**`, раз в сутки | полный прогон «виртуального врача» по всем отделениям, отчёт артефактом; заводится, когда отделений станет больше одного (этап 4), до того короткий прогон идёт в проверках `android.yml` |
| `.github/workflows/rustore.yml` | вручную — запускает владелец | перенос из «Вотчины» с `tools/store/rustore.mjs`: APK из релиза — последнего `vX.Y.Z` или того, чей тег указан, — в черновик новой версии RuStore по API; на модерацию — только с галочкой «submit». Работает, когда владелец заведёт ключ API RuStore ([«Выкладывание в RuStore»](#выкладывание-в-rustore)) |

**AAB для Google Play не собирается** (решение владельца, 03.10.2026: экономия минут
Actions; раньше его заказывали ручным запуском, которого больше нет). Workflow устроен
матрицей сборок, как в «Вотчине», и шаги сборки, проверок и релиза AAB понимают: вернуть его —
вторая строка матрицы в задании «Ключ подписи» (отдельная сборка из того же коммита: в одном
задании нельзя, Gradle не считает переменные окружения входом сборки JS).

| Файл | Куда | «Поддержать» | `EXPO_PUBLIC_STORE` |
|------|------|--------------|---------------------|
| `anamnez-N.apk` | Releases, RuStore, прочие магазины | есть | пусто |
| `anamnez-N.aab` — сейчас не собирается | Google Play | нет | `play` |

После сборки CI проверяет содержимое:

- **подпись** — отпечаток сертификата совпадает с переменной `ANDROID_CERT_SHA256`;
  у APK и AAB (если он собирается) один ключ;
- **разрешения** — ровно белый список; в отличие от «Вотчины», **без `INTERNET` и
  `ACCESS_NETWORK_STATE`** (ADR [0006](adr/0006-offline-no-internet.md); их убирает
  плагин только из релизного манифеста — отладочной сборке сеть нужна для Metro);
  `AD_ID`, значки лаунчеров, push, install referrer — вырезаны в `app.json`
  (`blockedPermissions`), любое лишнее разрешение — ошибка сборки. Белый список сейчас:
  `VIBRATE` (вибрация), `MODIFY_AUDIO_SETTINGS` (`expo-audio`, обычное разрешение без
  запроса у игрока) и служебное `games.gornitsa.anamnez.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`;
  окончательно сверяется с манифестом первой подписанной сборки. `WAKE_LOCK` объявляет
  плеер `media3-exoplayer` внутри `expo-audio` для режима «не засыпать при
  воспроизведении»; `expo-audio` этот режим не включает, поэтому разрешение вырезано в
  `app.json`;
- **бэкап** — правила автобэкапа включают только `saves/` и `profile.json`
  ([`07-data-model.md`](07-data-model.md) §4) — проверка появится вместе с настоящими
  сохранениями партии (этап 2);
- **16 КБ** — выравнивание нативных библиотек arm64-v8a; других архитектур в сборке нет:
  игра — для современных телефонов (NFR-PRF-1), 32-битные библиотеки почти вдвое
  увеличили бы APK;
- **target API** — не ниже требуемого Google Play (36 с 31.08.2026);
- **размер** APK печатается в итогах (NFR-SIZE-1);
- реквизиты «Поддержать» есть в бандле APK и отсутствуют в AAB — вместе с самим экраном
  (проверка AAB — когда он собирается).

Задание `release` выкладывает собранное одной публикацией: тег `vX.Y.Z` — релиз «Latest»,
описание — раздел версии из `README.md`, файл — APK. Тег сверяется с версией в `app.json` до сборки: `v0.3.2`
при версии 0.3.1 останавливает её до Gradle.

### Слияние

Кто сливает что — по ADR студии [0018](https://github.com/Nefeste/gornitsa/blob/main/adr/0018-change-classes-automerge.md)
и [`docs/04-process.md`](https://github.com/Nefeste/gornitsa/blob/main/docs/04-process.md#ветки-и-ci) устава. Здесь —
как это устроено в «Анамнезе»: обязательная проверка — «Проверки PR» (`pr.yml`); черновики базы
(`review: draft`) — того же класса, что документы. Пути владельца —
[`.github/CODEOWNERS`](../.github/CODEOWNERS): `.github/`, `app.json`, `store/forms.md`,
`store/privacy*`, а также `deploy/`, `server/`, `src/money/`, `eas.json` (их в «Анамнезе» пока
нет); такой PR сливает владелец, а автослияние пишет в нём, какие пути — владельца. Список
путей, их разбор и связи workflow держит `tools/test/guardrails.test.ts`. Защиту ветки `main` —
обязательный PR, обязательные «Проверки PR», ревью владельца кода, разрешённое автослияние —
включает владелец в настройках репозитория.

PR агентов создаются от учётной записи владельца, а автор не может одобрить свой PR. Поэтому
PR с путями владельца он сливает в обход правил защиты — галочкой «Merge without waiting for
requirements to be met» под кнопкой слияния. Обход доступен всему, что действует от этой
учётной записи, в том числе агентам: правило «агент не сливает» держится на `AGENTS.md`.
Почему у закрытых репозиториев нет защиты веток — [ADR студии 0017](https://github.com/Nefeste/gornitsa/blob/main/adr/0017-repo-visibility.md).

### Ключ подписи — постоянный с первой сборки

Решение — ADR [0015](adr/0015-ci-build-signing.md). «Вотчина» полгода подписывалась
общеизвестным отладочным ключом шаблона и потом переезжала на постоянный с
переустановкой у каждого игрока. Здесь этого не будет: **первый APK, который попадает
на чей-то телефон, уже подписан постоянным ключом.** Без секретов ключа CI собирает APK
только на проверку — манифест, разрешения, 16 КБ, размер — и выбрасывает его: ни
артефакта, ни релиза. AAB без ключа не собирается вовсе.

Плагин подписи `plugins/with-release-signing.js` переносится из «Вотчины» с заменой имён
свойств (`ANAMNEZ_UPLOAD_*`). Секреты и переменная — те же по смыслу:

| Секрет / переменная | Что лежит |
|---------------------|-----------|
| `ANDROID_KEYSTORE_BASE64` | файл ключа (`.jks`) в base64 |
| `ANDROID_KEYSTORE_PASSWORD` | пароль хранилища |
| `ANDROID_KEY_ALIAS` | псевдоним ключа |
| `ANDROID_KEY_PASSWORD` | пароль ключа |
| `ANDROID_CERT_SHA256` (переменная) | отпечаток сертификата; чужой ключ в секретах остановит сборку |

Ключ заводится один раз на своём компьютере (не в CI), **отдельный от ключа «Вотчины»**:

```bash
keytool -genkeypair -v -keystore anamnez-release.jks -alias anamnez \
  -keyalg RSA -keysize 4096 -validity 36500 -dname "CN=Anamnez"
base64 -w0 anamnez-release.jks > anamnez-release.jks.b64
keytool -list -v -keystore anamnez-release.jks -alias anamnez | grep SHA256
```

Файл `.jks` и пароли хранятся у владельца отдельно от репозитория: потерянный ключ — это
невозможность обновить игру никогда. В Play App Signing загружается **этот же ключ**
(не ключ Google), иначе APK из RuStore и сборка из Google Play перестанут обновлять друг
друга.

### Выкладывание в RuStore

Как в «Вотчине»: первую версию — через консоль RuStore, дальше — workflow
`rustore.yml` (секрет `RUSTORE_API_TOKEN`, переменная `RUSTORE_KEY_ID` — ключ API с
доступом к этой игре). Запускает владелец: Actions → RuStore → Run workflow. Без тега берётся
APK последнего релиза `vX.Y.Z` (старые пре-релизы `build-N` пропускаются). Черновик
ждёт в консоли RuStore; на модерацию он уходит галочкой «submit» или кнопкой в консоли.

## Как загружается код

По уставу студии ([`docs/04-process.md`](https://github.com/Nefeste/gornitsa/blob/main/docs/04-process.md#как-загружается-код)): коммитами в рабочую
ветку `claude/…` и PR, а без прямого доступа — через веб-интерфейс GitHub с проверкой `sha-256`.
На каждый PR идут быстрые проверки; APK собирается только по тегу версии (ADR студии 0019).

## Что делать, если контекст потерян

По уставу студии ([`docs/04-process.md`](https://github.com/Nefeste/gornitsa/blob/main/docs/04-process.md#если-контекст-потерян)): `AGENTS.md` устава,
потом [`docs/README.md`](README.md), история коммитов и разделы версий, [`10-roadmap.md`](10-roadmap.md)
и спецификация текущего этапа. Перед работой с базой — [`05-content.md`](05-content.md), §2 и §8 обязательно.
