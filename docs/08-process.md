# Как ведётся работа

Процесс повторяет «Вотчину» — он там проверен до магазинов. Здесь записано, что
переносится как есть, что меняется и что добавляется из-за медицинской базы.

## Жизненный цикл возможности

```
идея ──► спецификация ──► код и тесты ──► проверка ──► версия ──► сборка ──► установка
         docs/specs/       по спецификации   локально,     номер     CI         на телефон
                                             в браузере,   и README
                                             на телефоне
```

1. **Спецификация.** Новый файл в `docs/specs/` по образцу: зачем, что увидит игрок, данные,
   движок, неудачные случаи, критерии приёмки, чего здесь нет. Спецификация — договор:
   всё, что в ней не написано, обсуждается до кода.
2. **Код.** Сначала движок и его тесты, потом экраны. Каждый кусок проверяется сразу.
3. **Проверка** по [`09-testing.md`](09-testing.md). Минимум перед релизом: типы, линтер,
   тесты движка, валидатор базы, «виртуальный врач», сценарий возможности в браузере;
   для карты и звука — на телефоне.
4. **Документы.** Правятся `03`–`07`, если изменилось устройство; в `10-roadmap.md` этап
   переезжает в «сделано»; при важном решении — ADR.
5. **Версия и релиз** — по чек-листу ниже.

## Поток медицинской базы

Параллельно возможностям идёт наполнение базы (`05-content.md`). Для него спецификация
не пишется; порядок такой:

1. Пачка записей одного отделения (5–10 состояний со своими признаками и
   обследованиями), каждая — `review: draft`, с источниками.
2. `npm run content` — сборка и валидатор; `npm run doctor` — «виртуальный врач» по
   отделению. Отчёт (точность, цена, путаницы) — в описание коммита.
3. Сверка владельцем по источникам → `checked`; неотложные — консультанту → `reviewed`.
4. Поднять `contentVersion`, если пачка уходит в выпуск.

## Версии

Номер версии игры — как в «Вотчине»:

- **третье число** — исправления и мелочи, **второе** — заметная возможность или новое
  отделение, **первое** — смена обещания игроку. 1.0.0 — выход в магазины;
- `versionCode` — +1 при каждом релизе (Google Play не примет второй файл с тем же
  номером ни на одну дорожку);
- у базы — свой номер `contentVersion` (`content/version.yaml`), растёт при каждом
  выпуске с изменённой базой; оба номера видны в «Об игре» и в отчёте об ошибке.

### Где лежит номер версии

Как в «Вотчине», в нескольких местах; сверяет их `tools/test/version.test.ts`.

| Файл | Что поправить |
|------|---------------|
| `app.json` | `expo.version` и `expo.android.versionCode` (+1) |
| `package.json` | `version` |
| `package-lock.json` | `npm install --package-lock-only` (номер поднимается **до** установки) |
| `src/version.ts` | `APP_VERSION`, `APP_BUILD` = `versionCode` |
| `src/i18n/sections/settings.ts` | `whatsNew['X.Y.Z']` — «Что нового» |
| `content/version.yaml` | `contentVersion`, если база менялась |

Каждой версии — раздел в корневом `README.md`, человеческим языком, о том, что
изменилось для игрока.

## Сборка и выкладывание

Автоматика — перенос из «Вотчины» с правками. Сервера нет, поэтому `worker.yml` не нужен.

| Workflow | Когда | Что делает |
|----------|-------|------------|
| `.github/workflows/android.yml` | PR и загрузка в `main` (кроме `docs/`, `store/`); вручную | задание «проверки» на каждый PR: типы, линтер, тесты, сборка и валидатор базы, короткий прогон «виртуального врача»; на `main` — ещё веб-сборка со сценарием Playwright (не на PR — ради минут Actions; перед пушем сценарий гоняется локально), сборка APK и публикация в Releases; AAB — вручную (галочка `aab`) |
| `.github/workflows/doctor.yml` | изменения `content/**`, `src/engine/**`, раз в сутки | полный прогон «виртуального врача» по всем отделениям, отчёт артефактом; заводится, когда отделений станет больше одного (этап 4), до того короткий прогон идёт в проверках `android.yml` |
| `.github/workflows/rustore.yml` | вручную | перенос из «Вотчины» как есть: APK из последней публикации — в черновик новой версии RuStore по API; заводится к выходу в магазины (этап 7) |

Две сборки из одного коммита, параллельно, как в «Вотчине» (в одном задании нельзя:
Gradle не считает переменные окружения входом сборки JS). **Пока — только APK:** до выхода
в магазины AAB не нужен, а вторая сборка удваивает минуты Actions (решение владельца,
26.09.2026). AAB собирается вручную: Actions → Android → Run workflow с галочкой `aab`; к
выходу в Google Play (этап 7) — снова на каждую версию.

| Файл | Куда | «Поддержать» | `EXPO_PUBLIC_STORE` |
|------|------|--------------|---------------------|
| `anamnez-N.apk` | Releases, RuStore, прочие магазины | есть | пусто |
| `anamnez-N.aab` | Google Play | нет | `play` |

После сборки CI проверяет содержимое:

- **подпись** — отпечаток сертификата совпадает с переменной `ANDROID_CERT_SHA256`;
  у APK и AAB один ключ;
- **разрешения** — ровно белый список; в отличие от «Вотчины», **без `INTERNET` и
  `ACCESS_NETWORK_STATE`** (ADR [0006](adr/0006-offline-no-internet.md); их убирает
  плагин только из релизного манифеста — отладочной сборке сеть нужна для Metro);
  `AD_ID`, значки лаунчеров, push, install referrer — вырезаны в `app.json`
  (`blockedPermissions`), любое лишнее разрешение — ошибка сборки. Белый список сейчас:
  `VIBRATE` (вибрация), `MODIFY_AUDIO_SETTINGS` (`expo-audio`, обычное разрешение без
  запроса у игрока) и служебное `com.anamnez.game.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`;
  окончательно сверяется с манифестом первой подписанной сборки. `WAKE_LOCK` объявляет
  плеер `media3-exoplayer` внутри `expo-audio` для режима «не засыпать при
  воспроизведении»; `expo-audio` этот режим не включает, поэтому разрешение вырезано в
  `app.json`;
- **бэкап** — правила автобэкапа включают только `saves/` и `profile.json`
  ([`07-data-model.md`](07-data-model.md) §4) — проверка появится вместе с настоящими
  сохранениями партии (этап 2);
- **16 КБ** — выравнивание нативных библиотек arm64-v8a; других архитектур в сборке нет:
  игра — для современных телефонов (NFR-PRF-1), 32-битные библиотеки почти вдвое
  увеличили бы APK;
- **target API** — не ниже требуемого Google Play (36 с 31.08.2026);
- **размер** APK печатается в итогах (NFR-SIZE-1);
- реквизиты «Поддержать» есть в бандле APK и отсутствуют в AAB — вместе с самим экраном.

Задание `release` выкладывает собранное одной публикацией: первая сборка новой версии —
релиз `vX.Y.Z` («Latest»), описание — раздел версии из `README.md`; всякая другая —
пре-релиз `build-N`.

### Ключ подписи — постоянный с первой сборки

Решение — ADR [0015](adr/0015-ci-build-signing.md). «Вотчина» полгода подписывалась
общеизвестным отладочным ключом шаблона и потом переезжала на постоянный с
переустановкой у каждого игрока. Здесь этого не будет: **первый APK, который попадает
на чей-то телефон, уже подписан постоянным ключом.** Без секретов ключа CI собирает APK
только на проверку — манифест, разрешения, 16 КБ, размер — и выбрасывает его: ни
артефакта, ни релиза. AAB без ключа не собирается вовсе.

Плагин подписи `plugins/with-release-signing.js` переносится из «Вотчины» с заменой имён
свойств (`ANAMNEZ_UPLOAD_*`). Секреты и переменная — те же по смыслу:

| Секрет / переменная | Что лежит |
|---------------------|-----------|
| `ANDROID_KEYSTORE_BASE64` | файл ключа (`.jks`) в base64 |
| `ANDROID_KEYSTORE_PASSWORD` | пароль хранилища |
| `ANDROID_KEY_ALIAS` | псевдоним ключа |
| `ANDROID_KEY_PASSWORD` | пароль ключа |
| `ANDROID_CERT_SHA256` (переменная) | отпечаток сертификата; чужой ключ в секретах остановит сборку |

Ключ заводится один раз на своём компьютере (не в CI), **отдельный от ключа «Вотчины»**:

```bash
keytool -genkeypair -v -keystore anamnez-release.jks -alias anamnez \
  -keyalg RSA -keysize 4096 -validity 36500 -dname "CN=Anamnez"
base64 -w0 anamnez-release.jks > anamnez-release.jks.b64
keytool -list -v -keystore anamnez-release.jks -alias anamnez | grep SHA256
```

Файл `.jks` и пароли хранятся у владельца отдельно от репозитория: потерянный ключ — это
невозможность обновить игру никогда. В Play App Signing загружается **этот же ключ**
(не ключ Google), иначе APK из RuStore и сборка из Google Play перестанут обновлять друг
друга.

### Выкладывание в RuStore

Как в «Вотчине»: первую версию — через консоль RuStore, дальше — workflow
`rustore.yml` (секрет `RUSTORE_API_TOKEN`, переменная `RUSTORE_KEY_ID` — ключ API с
доступом к этой игре).

## Чек-лист релиза

- [ ] `npx tsc --noEmit -p .` и `-p tools` — без ошибок
- [ ] `npm run lint` — ни ошибок, ни предупреждений
- [ ] `bun test` — тесты движка
- [ ] `npm run content` — база собрана, валидатор зелёный; `contentVersion` поднят, если база менялась
- [ ] `npm run doctor` — пороги «виртуального врача» выполнены (`05-content.md` §6)
- [ ] сценарии в браузере (`09-testing.md`)
- [ ] на современном телефоне: карта без подвисаний, звук, вибрация, обновление поверх прошлой версии
- [ ] версия поднята во всех местах, `versionCode` +1
- [ ] «Что нового» — в `src/i18n/sections/settings.ts` и `store/listing.*.md`; изменились
      экраны — `npm run export:web && npm run store` и снимки посмотреть глазами
- [ ] раздел версии в `README.md`
- [ ] документы и дорожная карта поправлены
- [ ] сборка зелёная, APK в Releases (AAB — вручную, перед выкладкой в Google Play), отпечаток ключа — ожидаемый
- [ ] AAB — в Play Console, APK — в RuStore (с 1.0)

## Как загружается код

Если у ассистента есть `git push` (облачная сессия Claude Code с доступом GitHub App к
репозиторию), код загружается коммитами в рабочую ветку `claude/…`, в `main` попадает
слиянием; CI собирает APK только по загрузке в `main`. Если прямого доступа нет —
порядок переноса файлов через веб-интерфейс описан в «Вотчине» (`docs/05-process.md`,
«Как загружается код») и подходит без изменений.

Изменения, которые не должны запускать сборку (только документы), помечаются
`[skip ci]` в заголовке коммита.

## Что делать, если контекст потерян

Ассистент, начинающий с нуля, должен:

1. Прочитать [`docs/README.md`](README.md) и дальше по списку.
2. Посмотреть `git log` и разделы версий в корневом `README.md` — это состояние.
3. Открыть [`10-roadmap.md`](10-roadmap.md) — там написано, что делается прямо сейчас.
4. Открыть спецификацию текущего этапа в `docs/specs/`.
5. Перед работой с базой — [`05-content.md`](05-content.md), §2 и §8 обязательно.
